# 🚚 Delivery Analytics API

![Python](https://img.shields.io/badge/Python-3.12-3776AB?logo=python&logoColor=white)
![FastAPI](https://img.shields.io/badge/FastAPI-0.125.0-009688?logo=fastapi&logoColor=white)
![MongoDB](https://img.shields.io/badge/MongoDB-7-47A248?logo=mongodb&logoColor=white)
![Docker](https://img.shields.io/badge/Docker-Compose-2496ED?logo=docker&logoColor=white)

REST API для хранения заказов доставки, расчёта бизнес-показателей и анализа времени обработки HTTP-запросов. Проект объединяет FastAPI, агрегации MongoDB и собственное логирование запросов, а генератор синтетических логов позволяет наполнить базу данными для проверки метрик.

## ✅ Основные возможности

- ✅ Создание отдельных заказов и пакетная загрузка.
- ✅ Получение заказа по идентификатору.
- ✅ Фильтрация заказов по статусу, ресторану и пользователю, пагинация через `skip` и `limit`.
- ✅ Обновление стоимости и статуса заказа.
- ✅ Топ-5 ресторанов по сумме стоимости заказов.
- ✅ Расчёт доли отменённых заказов.
- ✅ Распределение количества заказов по дням недели.
- ✅ Сохранение пути, метода, времени обработки и HTTP-статуса запросов в MongoDB.
- ✅ Расчёт p50, p95, p99, среднего RPS и количества серверных ошибок за выбранный период.
- ✅ Генерация синтетических логов со случайными задержками и статусами.
- ✅ Запуск приложения и MongoDB через Docker Compose.

## 🏗 Архитектура

```text
HTTP-клиент / Swagger UI / Postman
                |
                v
       FastAPI: app/main.py
                |
       HTTP middleware
       |                |
       v                v
     Роутеры       LoggingService
       |                |
       |                +-------------------+
       v                                    v
 orders / analytics                   MongoDB: logs
       |                                    ^
       v                                    |
 MongoDB: orders                   logs / metrics
                                            |
                                   random_service
                               (синтетические логи)
```

В `app/main.py` подключены четыре роутера без дополнительных префиксов:

- `orders.router` — работа с заказами;
- `analytics.router` — бизнес-аналитика;
- `logs.router` — генерация логов;
- `metrics.router` — технические метрики.

`database.py` читает `MONGODB_URI` из окружения. По умолчанию используется `mongodb://localhost:27017`. Имя базы зафиксировано в коде: `delivery_service`; коллекции — `orders` и `logs`.

Middleware измеряет время до получения ответа от обработчика, затем синхронно записывает лог. Время самой записи лога в `duration_ms` не входит. Если обработчик выбрасывает необработанное исключение, выполнение до записи лога не доходит.

### О примерах

Поля ответов ниже соответствуют моделям и возвращаемым значениям обработчиков. Данные заказов взяты из Postman-коллекции проекта.

В репозитории нет сохранённых HTTP-ответов: массивы `response` в Postman-коллекции пустые. Поэтому примеры показывают ожидаемые ответы по коду, а не результаты выполненного интеграционного теста. Значение `<generated_id>` обозначает строковый ObjectId, который MongoDB создаёт при вставке; при запросах заменяйте его реальным `id`.

### 1. `POST /orders`

Создаёт заказ. Тело запроса соответствует `OrderCreate`.

```json
{
  "user": "Иван Петров",
  "restaurant": "Пиццерия Маргарита",
  "total_price": 1200.0,
  "status": "DELIVERED",
  "items": [
    {
      "dish": "Пицца Маргарита",
      "quantity": 2,
      "price": 600.0
    }
  ],
  "created_at": "2026-10-11T12:30:00"
}
```

Ответ `201`:

```json
{
  "id": "<generated_id>",
  "user": "Иван Петров",
  "restaurant": "Пиццерия Маргарита",
  "total_price": 1200.0,
  "status": "DELIVERED",
  "items": [
    {
      "dish": "Пицца Маргарита",
      "quantity": 2,
      "price": 600.0
    }
  ],
  "created_at": "2026-10-11T12:30:00"
}
```

Обязательные поля: `user`, `restaurant`, `total_price`, `items`. Если не передать `status`, используется `"CREATED"`; `created_at` по умолчанию заполняется через `datetime.now()`.

Стоимость передаётся клиентом: сервер не пересчитывает её по позициям заказа. Статус — произвольная строка, ограничения перечнем значений нет.

### 2. `GET /orders`

Параметры запроса:

| Параметр | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `status` | string | Не задан | Точное совпадение статуса |
| `restaurant` | string | Не задан | Точное совпадение ресторана |
| `user` | string | Не задан | Точное совпадение пользователя |
| `skip` | integer | `0` | Количество пропускаемых записей |
| `limit` | integer | `50` | Лимит возвращаемых записей |

Фильтры можно сочетать. Явная сортировка не задана.

Пример запроса:

```http
GET /orders?status=DELIVERED&skip=0&limit=1
```

Пример ответа, если выборка содержит созданный выше заказ:

```json
[
  {
    "id": "<generated_id>",
    "user": "Иван Петров",
    "restaurant": "Пиццерия Маргарита",
    "total_price": 1200.0,
    "status": "DELIVERED",
    "items": [
      {
        "dish": "Пицца Маргарита",
        "quantity": 2,
        "price": 600.0
      }
    ],
    "created_at": "2026-10-11T12:30:00"
  }
]
```

При отсутствии совпадений возвращается `[]`. Общее количество записей в ответ не включается.

### 3. `GET /orders/{order_id}`

Возвращает заказ по MongoDB ObjectId.

```http
GET /orders/<generated_id>
```

Ответ `200` для созданного выше заказа:

```json
{
  "id": "<generated_id>",
  "user": "Иван Петров",
  "restaurant": "Пиццерия Маргарита",
  "total_price": 1200.0,
  "status": "DELIVERED",
  "items": [
    {
      "dish": "Пицца Маргарита",
      "quantity": 2,
      "price": 600.0
    }
  ],
  "created_at": "2026-10-11T12:30:00"
}
```

Для некорректного формата ObjectId обработчик возвращает `404`:

```json
{
  "detail": "Заказ не найден"
}
```

**Текущее ограничение:** корректный по формату, но отсутствующий в БД идентификатор не обрабатывается отдельно и приводит к серверной ошибке.

### 4. `POST /orders/bulk`

Принимает массив объектов `OrderCreate`.

```json
[
  {
    "user": "Иван Петров",
    "restaurant": "Пиццерия Маргарита",
    "total_price": 1200.0,
    "status": "DELIVERED",
    "items": [
      {
        "dish": "Пицца Маргарита",
        "quantity": 2,
        "price": 600.0
      }
    ],
    "created_at": "2026-10-11T12:30:00"
  }
]
```

Ответ `201` для массива из одного заказа:

```json
{
  "inserted_count": 1,
  "inserted_ids": [
    "<generated_id>"
  ]
}
```

В Postman-коллекции подготовлен пакет из 50 заказов. В его исходных объектах есть поле `id`, но оно не входит в `OrderCreate` и игнорируется при валидации. MongoDB создаёт новые идентификаторы.

Пустой массив отдельно не проверяется и вызывает ошибку при `insert_many`.

### 5. `PUT /orders/{order_id}`

Обновляет только `total_price` и/или `status`. Несмотря на метод PUT, обработчик выполняет частичное обновление через `$set`.

```http
PUT /orders/<generated_id>
Content-Type: application/json
```

```json
{
  "status": "CANCELLED"
}
```

Ответ `200` после изменения ранее созданного заказа:

```json
{
  "id": "<generated_id>",
  "user": "Иван Петров",
  "restaurant": "Пиццерия Маргарита",
  "total_price": 1200.0,
  "status": "CANCELLED",
  "items": [
    {
      "dish": "Пицца Маргарита",
      "quantity": 2,
      "price": 600.0
    }
  ],
  "created_at": "2026-10-11T12:30:00"
}
```

Поля со значением `null` исключаются из обновления. Если обновлять нечего, возвращается `400`:

```json
{
  "detail": "Нет данных для обновления"
}
```

Для корректного ObjectId отсутствующего заказа здесь также не предусмотрена проверка результата поиска.

### 6. `GET /analytics/revenue`

```http
GET /analytics/revenue
```

Группирует заказы по ресторану, суммирует `total_price`, сортирует сумму по убыванию и возвращает первые пять ресторанов.

Ожидаемый ответ для 50 заказов из Postman-коллекции, загруженных один раз в пустую коллекцию:

```json
[
  {"restaurant": "Суши-бар Токио", "total_revenue": 26900.0},
  {"restaurant": "Итальянская траттория", "total_revenue": 21700.0},
  {"restaurant": "Пиццерия Маргарита", "total_revenue": 17000.0},
  {"restaurant": "Китайская кухня", "total_revenue": 16000.0},
  {"restaurant": "Бургерная", "total_revenue": 11000.0}
]
```

**Особенность расчёта:** учитываются все статусы, включая `CANCELLED`. Это сумма заявленной стоимости заказов, а не подтверждённых оплат. Фильтра периода нет.

Для пустой коллекции возвращается `[]`.

### 7. `GET /analytics/cancelled`

```http
GET /analytics/cancelled
```

Считает все заказы и заказы со статусом строго `"CANCELLED"`.

Ожидаемый ответ для исходного пакета из Postman:

```json
{
  "total_orders": 50,
  "cancelled_orders": 2,
  "cancelled_rate": 0.04
}
```

`cancelled_rate` — доля, а не процент: `0.04` соответствует 4%.

**Текущее ограничение:** на пустой коллекции обработчик обращается к отсутствующему первому элементу результата агрегации и завершается ошибкой. Перед проверкой создайте хотя бы один заказ.

### 8. `GET /analytics/business`

```http
GET /analytics/business
```

Группирует заказы по дню недели поля `created_at`.

Ожидаемый ответ для исходного пакета из Postman:

```json
[
  {"total_orders": 11, "day": "Sunday"},
  {"total_orders": 7, "day": "Monday"},
  {"total_orders": 7, "day": "Tuesday"},
  {"total_orders": 7, "day": "Wednesday"},
  {"total_orders": 6, "day": "Thursday"},
  {"total_orders": 6, "day": "Friday"},
  {"total_orders": 6, "day": "Saturday"}
]
```

Порядок — от воскресенья до субботы. Дни без заказов не добавляются, для пустой коллекции возвращается `[]`. В `$dayOfWeek` часовой пояс явно не задан.

### 9. `POST /logs/generate_fake`

Создаёт синтетические записи непосредственно в коллекции `logs`.

Запрос на одну запись за последние сутки:

```json
{
  "number_of_logs": 1,
  "days": 1
}
```

Ответ `200` — массив строковых идентификаторов созданных логов:

```json
[
  "<generated_log_id>"
]
```

В Postman-коллекции используется запрос на 100 записей:

```json
{
  "number_of_logs": 100,
  "days": 1
}
```

Особенности генерации:

- путь и метод выбираются из OpenAPI-схемы приложения;
- маршрут генератора и служебные страницы исключены;
- время записи выбирается случайно в указанном диапазоне;
- статус `200` выбирается с вероятностью 98%, `505` — 2%;
- задержки генерируются с обычными, медленными и очень медленными значениями;
- маршруты с параметрами сохраняются как шаблоны, например `/orders/{order_id}`.

Генератор не выполняет реальные HTTP-запросы. При этом сам вызов генератора дополнительно записывается middleware как обычный запрос.

### 10. `GET /metrics`

| Параметр | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `time` | float | `1` | Период анализа в часах |

Пример из Postman-коллекции — последние шесть минут:

```http
GET /metrics?time=0.1
```

Ответ, когда в выбранном окне нет логов:

```json
[]
```

При наличии записей возвращается массив с одним объектом:

| Поле | Значение |
|---|---|
| `total_requests` | Количество логов в окне |
| `total_errors` | Количество записей со `status_code >= 500` |
| `p50` | Элемент отсортированных задержек с индексом `floor(N / 2)` |
| `p95` | Элемент с индексом `floor(N × 0.95)` |
| `p99` | Элемент с индексом `floor(N × 0.99)` |
| `rps` | `N / (time × 3600)` |

Задержки измеряются в миллисекундах. Перцентили выбираются по индексам массива без интерполяции; `rps` — средняя частота за всё запрошенное окно.

Числовые результаты зависят от сохранённых логов и случайных значений генератора, поэтому фиксированного ответа с метриками в репозитории нет.

Передавайте положительный `time`: ограничение на уровне валидации не задано. Реальные и синтетические записи участвуют в общем расчёте. Текущий запрос `/metrics` логируется после расчёта и не входит в собственный ответ.

## 🚀 Быстрый старт

### Вариант 1. Docker Compose

Из корневой директории проекта:

```bash
docker compose up --build
```

Если установлен отдельный исполняемый файл `docker-compose`, эквивалентная команда:

```bash
docker-compose up --build
```

Compose запускает:

- `api` — приложение на порту `8000`;
- `mongo` — MongoDB 7 на порту `27017`;
- именованный том `mongo_data` — постоянное хранилище базы.

Внутри контейнера API используется:

```text
MONGODB_URI=mongodb://mongo:27017/delivery_service
```

После запуска откройте:

- [Swagger UI](http://localhost:8000/docs);
- [ReDoc](http://localhost:8000/redoc);
- [OpenAPI JSON](http://localhost:8000/openapi.json).

Корневой маршрут `/` в приложении не определён.

Для остановки:

```bash
docker compose down
```

Обычная остановка не удаляет именованный том с данными.

`depends_on` задаёт порядок запуска, но healthcheck MongoDB в Compose не настроен. Если первый запрос пришёл до готовности БД, повторите его после завершения запуска MongoDB.

> **Примечание для Windows**
>
> Для запуска через Docker Desktop используйте Linux-контейнеры и включённый backend WSL 2. Убедитесь, что Docker Desktop запущен, а порты `8000` и `27017` свободны. Команды Compose можно выполнять из PowerShell в корне проекта.

### Вариант 2. Локальный запуск

Понадобятся Python 3.12 и доступная MongoDB 7.

При наличии Docker можно запустить только базу из Compose:

```bash
docker compose up -d mongo
```

Создайте виртуальное окружение:

```bash
python -m venv .venv
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Установите зависимости:

```bash
python -m pip install -r requirements.txt
```

Для MongoDB по адресу `localhost:27017` дополнительная настройка не нужна. При другом адресе задайте переменную окружения.

Linux/macOS:

```bash
export MONGODB_URI="mongodb://localhost:27017"
```

Windows PowerShell:

```powershell
$env:MONGODB_URI = "mongodb://localhost:27017"
```

Приложение читает окружение через `os.getenv`; автоматическая загрузка `.env` не реализована.

Запустите API из корня проекта:

```bash
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Если активация окружения в PowerShell недоступна, можно использовать интерпретатор напрямую:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

## 💡 Ключевые технические решения

1. **Аналитика средствами MongoDB.**  
   Группировка, суммирование, сортировка и расчёт долей выполняются в aggregation pipelines. Для дней недели используются `$dayOfWeek` и `$switch`, для перцентилей — `$sortArray` и `$arrayElemAt`.

2. **Единый сервис записи логов.**  
   `LoggingService` используется и HTTP middleware, и генератором. Записи имеют общие поля: `timestamp`, `endpoint`, `method`, `duration_ms`, `status_code`.

3. **Генерация маршрутов по OpenAPI.**  
   Генератор получает пути и методы из схемы приложения. Для выбора маршрутов не требуется отдельный вручную поддерживаемый список.

4. **Модель задержек с редкими выбросами.**  
   Генератор выбирает обычные задержки с вероятностью 95%, медленные — 4%, очень медленные — 1%. Для них используются нормальные распределения с параметрами `50 ± 15`, `300 ± 100` и `3000 ± 1000` мс соответственно; отрицательные значения ограничиваются нулём.

## 🧪 Тестирование

В репозитории есть Postman-коллекция для ручной проверки. Автоматизированного набора тестов нет.

### Проверка через Swagger UI

1. Запустите приложение и откройте [Swagger UI](http://localhost:8000/docs).
2. Выполните `POST /orders` с примером из API Reference.
3. Убедитесь, что получен статус `201`, и сохраните возвращённый `id`.
4. Вызовите `GET /orders/{order_id}` с этим идентификатором.
5. Проверьте `GET /orders` с фильтром `status=DELIVERED`.
6. Измените статус на `CANCELLED` через `PUT /orders/{order_id}`.
7. Повторно получите заказ и проверьте новое значение.
8. Вызовите три аналитических маршрута. Если в базе только этот заказ:
   - сумма для ресторана будет `1200.0`, в том числе после отмены;
   - доля отмен будет `1.0`;
   - в распределении по дням будет один заказ в `Sunday`.
9. Выполните `POST /logs/generate_fake` с телом:

   ```json
   {
     "number_of_logs": 100,
     "days": 1
   }
   ```

10. Проверьте, что ответ содержит 100 идентификаторов.
11. Вызовите `GET /metrics?time=24` и проверьте наличие полей метрик. Количество запросов включает как синтетические записи, попавшие в окно, так и обычные запросы API.
12. Проверьте предусмотренные ошибки:
    - `GET /orders/not-an-object-id` → `404`;
    - `PUT /orders/{order_id}` с `{}` → `400`;
    - `POST /orders` без обязательных полей → `422`.

### Проверка через Postman

1. Импортируйте `postman/postman_collection.json`.
2. Используйте адрес `http://127.0.0.1:8000`, указанный в коллекции.
3. Для проверки приведённых аналитических результатов загрузите пакет `/orders/bulk` **один раз в пустую коллекцию заказов**.
4. Проверьте `inserted_count: 50`, затем вызовите аналитические маршруты.
5. Замените фиксированный идентификатор в сохранённом PUT-запросе на один из фактически возвращённых `inserted_ids`.
6. Выполните генерацию логов и запрос метрик.

Повторная отправка пакетного запроса создаёт новые заказы: дедупликация не реализована. Это изменит суммы и количество записей.

### Текущие ограничения

- Нет аутентификации и разграничения доступа.
- Отсутствующие заказы с корректным ObjectId не обрабатываются корректно в GET и PUT.
- Расчёт доли отмен не поддерживает пустую коллекцию.
- Не заданы ограничения на положительность цен, количества, периода метрик и параметров генерации.
- Синтетические и реальные логи хранятся совместно без признака происхождения.
- Индексы и TTL для логов явно не создаются.
- При каждом вызове функций подключения создаётся новый `MongoClient`; централизованное управление его жизненным циклом отсутствует.
- Запись логов из асинхронного middleware выполняется синхронным драйвером.
- Перцентили требуют собрать и отсортировать все задержки выбранного окна.
